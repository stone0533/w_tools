# 使用反馈（库侧）

消费方用 `w_tools_*` 撞到的问题在这里汇总、定状态；**这里是唯一真相**。
默认**直接写这里**（不要再在消费方项目里维护第二份）；
只有拿不到本仓库时，才在消费方建 `docs/agents/<包>-feedback.md` 做缓冲、事后再同步进来。

## 规则

1. **有反馈才建文件**：`docs/feedback/<包>.md`，没有反馈的包不要建空文件。
2. **消费方只追加 `待处理`**，默认**直接写库侧文件**（有仓库访问权时）；
   `已确认` / `已修复` / `不修` 由维护者写。
3. `已修复` **必须带版本号**（最好再带 commit）；只写「修好了」等于没修。
4. 确认后**必须链 issue**（GitLab / GitHub），反馈日志不替代 issue tracker。
5. 已闭环条目压成表格一行，细节留在 CHANGELOG，**不做第二份 CHANGELOG**。
6. `待处理` 超过 30 天没动 → 标 `stale`（CI 会提示）。

## 目录约定

| 位置 | 放什么 |
|---|---|
| `docs/feedback/` | 反馈记录（**人读、需评审、不可再生成**） |
| `.w_tools/`（消费方项目） | 工具状态（manifest / 缓存，**删了能重建**） |

> 一句话：**`.w_tools/` 只放「删了能重建」的东西；反馈进 `docs/`。**

## 状态机

```
待处理 ──(维护者确认)──> 已确认(链 issue) ──(发布)──> 已修复(版本 + commit)
   └────────(不修)────> 不修(必须写理由)
```

## 模板

复制 [TEMPLATE.md](TEMPLATE.md) 里的一段，按字段填。

## AI 使用方法

- 写之前先 `grep -rn "<关键词>" docs/feedback/`，避免重复条目（重复的折叠成一行「同 #已有条目」）；
- 只追加 `### [待处理]`；不改状态、不删别人的条目；
- 一次会话最多写 3–5 条，**只记真正卡住你的**；「我觉得可以更好」不算；
- 提交前跑 `bash scripts/check_feedback.sh`（已闭环版本号 / 索引数量 / stale）；
- 拿不到本仓库时，才在消费方项目写 `docs/agents/<包>-feedback.md`，事后再同步进来。
